# Reconcile Order schema drift with an idempotent migration, not a production baseline

`prisma/schema.prisma`'s `Order` model (firstName/lastName, addressLine1/city/state/zip, paypalOrderId) diverged from the checked-in migration history — the historical migrations still produce the original `customerName`/`address`/`paymentStatus` shape, meaning `prisma migrate deploy` against a fresh database wouldn't match what the app code expects. Production itself already has the current shape (confirmed by the app working), almost certainly from an undocumented `prisma db push` at some point — the same pattern already seen once in `20260620000000_processing_and_paypal_ids` ("schema was ahead of migrations").

Rather than have someone manually run `prisma migrate resolve --applied` against production to baseline a migration without executing it, `20260826000000_reconcile_order_schema_drift` is written idempotently (`information_schema` checks, `ADD COLUMN IF NOT EXISTS`, `DROP COLUMN IF EXISTS`). It safely no-ops against a database that already has the current shape, and correctly backfills/migrates one that doesn't. This trades a slightly unusual-looking migration file for a `prisma migrate deploy` that stays a single, uniform, no-manual-steps path for every environment.
